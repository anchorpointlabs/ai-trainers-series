# Follow troubleshooting procedures

> **TSC #2 Prompt Design · Basic · Ability A4**

**IMDA requirement:** Follow standard troubleshooting procedures.

**What it means:** When a chat AI, a computer tool you can type requests into, does not reply, follow a safe sequence rather than guessing the cause. Record what you see, check the service and connection, change one thing and retry once, then check the result. If it still fails, escalate it: pass the facts to the support team.

**The learner must be able to:**
- Record an error and its time without including personal or sensitive information.
- Check a service-status page, the provider's page reporting service problems, and whether an approved public website loads.
- Demonstrate, in a simulation, a single retry in a new chat using the same harmless request, then compare the result with the original error.
- Prepare a short report for information technology (IT) support if the issue remains unresolved.

**Lesson Plan Ideas:**
1. Ask: “A chat gives an error instead of a reply. What should you do before changing settings or trying repeatedly?” Take two suggestions. 
2. Use the invented case below to show the sequence: note the error and time without private details; check the service-status page and an approved public website; start a new chat and retry the same harmless request once; check the result; report it to IT support if it still fails. If it works, record success and stop. A clear status page and a loading website do not prove the cause. Leave security settings alone; for real problems, follow workplace and provider guidance. 
3. In pairs, read the case in the prompt and role-play the actions in order. Write your own five-step record and support message before running the prompt, then compare both your work and the AI's model answer with the check below. Do not perform real service checks or send a real support message. 
4. Debrief: which step was missed, and did anyone mistake the checks for proof of a cause? Correct the record together. 

**Exercise (with the exact prompt):**
*Setup: pairs need access to a chat AI and paper; all checks and actions in the case are simulated.*

```
This is a simulation. Do not access websites, send messages or claim to have checked a real service.

Invented case: At 10:15 on 15 November 2026, Singapore time, a user asked a web-based AI chat: "List two ways to save water." The screen showed "There was an error generating a response." The provider's fictional status page reports no known incident, and an approved public website loads. When the user starts a new chat and retries exactly the same request once, the same error appears. No other changes were made.

Produce a model action record for a learner to compare with their own. Use five numbered steps in order: record the error and time without sensitive information; check the fictional service status and connection evidence; isolate the chat session by using a new chat and retrying the same request once; check the retry result without guessing its cause; escalate the unresolved issue to IT support. End with a short support message containing the error, time, status and connection checks, the retry and its result. Treat all checks and actions as simulated. Do not suggest disabling security controls or include names, passwords or private conversation content.
```

Expected result: a simulated five-step action record and a support message; the repeated error remains unresolved, not diagnosed.
What to check: both records show, in order, (1) the error and its time without sensitive data; (2) no known incident and a public website loading; (3) the same request retried once in a new chat with no other changes; (4) the same error after retry with no claimed cause; and (5) a support message with the error, time, both checks and the failed retry.

**Common mistakes:**
- Repeating the request or changing several settings — change only the chat session and retry the harmless request once in this case.
- Treating a loading website or clear status page as proof of the cause — record the checks and result without guessing.
- Sending a private conversation or password to support — share only the safe error, time, checks and retry result.
